# 审批流 AI 架构

以独立产品落地，不兼容旧流程格式。借鉴 DyOffice 的流式 AgentLoop、按身份注册工具及提议和确认分离；不引入 Office 编辑器、文件租约或 Office 工具。首版只需要一个助手。

## 数据路径
1. 用户将 PNG/JPG/PDF/DOCX 源材料关联到项目。真正接入时，网关校验类型、权限和大小，解析服务在隔离环境读取材料并按模型能力交付。
2. 图片直接作为模型输入。支持 PDF 原生视觉的模型优先接收 PDF；否则把选定页面按预算渲染成图。Word 优先模型原生支持；否则提取文档正文及结构、保留原有图片或渲染为页图。**不部署 OCR**。不得把文本抽取当成已读取扫描图。
3. 多模态模型通过按用户、项目、环境和当前会话筛选的工具获得草稿、字段、角色和环境能力。文件内容是不可信数据，不是工具调用指令；检索内容不含服务凭据。引文采用受控文件引用、页码或图像区域。
4. 新建可提完整候选，已有流程默认提小范围补丁。服务端校验类型、稳定 ID、条件和路径，提议绑定目标环境、目录版本、草稿版本和业务内容哈希。前端以节点/边高亮差异。过期提议不得自动重放。
5. 只有用户明确确认，服务端才在版本校验后的同一事务内应用并留恢复快照。设计预演不是 Odoo 真实试跑；真实试跑在隔离测试环境进行。发布另有能力、试跑和授权门禁，不交给模型。

| 工具 | 能力 |
|---|---|
| workflow.get_draft | 返回授权的、指定版本的流程定义 |
| workflow.get_catalog | 当前环境字段、角色、可用节点和条件 |
| workflow.propose_patch | 生成只读候选或结构化补丁，不能写草稿 |
| workflow.validate_patch | 检查边、条件类型、字段和环境能力 |
| workflow.preview_patch | 生成可定位的差异和材料依据 |
| workflow.simulate_route | 输入样例数据，返回路径和理由，不运行真实审批 |

apply_proposal、publish、Odoo 业务写入不开放为模型工具。本仓库提供工具定义与运行核心，企业试点入口未启用模型、材料上传、OCR 或 Odoo 调用。

## 实现顺序和验收

```text
Chat/RPC → 会话与上下文构建 → AgentLoop ↔ ModelAdapter
                                  ↕
                            授权 ToolRegistry
                                  ↓
                          提案、校验、路径预演
                                  ↓
               用户单独确认 → 草稿版本比对 + 应用 + 快照
```

- **运行核心**：与页面无关。ModelAdapter 输出文本增量和工具请求，AgentLoop 回传工具结果并限制轮次和工具次数，接收取消信号。用户、项目、环境从服务端认证上下文来，不接受模型在参数里改身份或目标环境。
- **材料输入**：用服务端有权限的材料引用构建模型输入；文档解析和页图转换只处理可确认的文件。模型返回的引用须验证是否存在且当前用户可见；无法核对的证据不能标为已核对。
- **业务工具**：复杂改动分解成明确操作（例如 update_condition 指定稳定 edgeId、字段、比较符和值）。已有关联条件时只给出要改的属性；审批人、其他分支以及节点位置均不应被改写。
- **环境门禁**：实际工具数据必须从目标环境读取，默认只读。一次预演结果只能证明当前图、样例、环境和版本，绝不等同正式发布或真实审批。
- **一致性用例**：先自动检查 49,999 / 50,000 / 50,001；提案改为 80,000 后检查 79,999 / 80,000 / 80,001。同一版本拒绝不认识的工具、类型不匹配的参数以及工具中伪造的身份；中途切换环境或草稿修订后，必须重新确认。

## v0.2 服务端切片

`src/responses-provider.ts` 实现 OpenAI Responses 流式适配。外部地址由代码固定，凭据由服务端注入，不能经浏览器、材料或工具参数携带。适配器读取授权材料一次，每轮为保留上下文会重传初始材料；使用 `store:false`，不把此选项宣传为零数据留存。项目部署前须确认供应商的数据条款。模型端的处理方式见 [OpenAI 文件输入](https://developers.openai.com/api/docs/guides/file-inputs)：PNG/JPEG 是视觉输入，PDF 包含文本与页面图像，DOCX 原生输入只含正文文本。需要识别 Word 内嵌流程图时，先在可信环境转成 PDF；本版本未附转换服务，不使用 OCR。原件授权、内容类型核验和受限文件读取由宿主实现。

`src/proposal-store.ts` 为本地参考存储。提案绑定创建它的用户、项目、环境、流程和草稿修订，有有效期。确认在单个事务中重验当前草稿、保留旧稿、应用一条变更并生成回执；相同用户重复确认同一提案返回同一回执，不重复写入。该切片仅支持采购金额门槛操作，不支持任意模型定义的补丁。

`src/ai-http.ts` 是 Fetch 兼容的服务适配器：

- `GET /v1/ai/workflows/:workflowId` 读取已授权草稿。
- `POST /v1/ai/workflows/:workflowId/turn` 接收 `{input, materialIds?}`，流式返回 NDJSON：`text`、可选 `proposal`、`done`；遇错则运行以 `error` 终止。只有可信工具结果和正常结束能创建待确认提案。
- `GET /v1/ai/workflows/:workflowId/proposals/:proposalId` 重新打开提案。
- `POST /v1/ai/workflows/:workflowId/proposals/:proposalId/confirm` 接收 `{expectedRevision}`，只接受显式人工确认权限，解析请求后还会重新核验权限。旧修订返回 409。

本包没有公开运行上述入口。挂载时必须实现用户认证、流程授权、材料 ACL、限速、载入目录及超时；使用 Cookie 时还要做 CSRF 校验。当前企业前端不会调用上述 AI 入口。测试使用官方协议形状的模拟响应；没有真实模型调用，也没有给模型生产材料，更没有 Odoo 访问或发布。

集成顺序：服务启动时创建 `ProposalStore`，确保仅服务账户可访问数据库目录；使用服务端配置构造 `createResponsesProvider({model, apiKey, resolveMaterial})`；将它与 `authorize`、`catalog` 和 `resolveMaterials` 一起传给 `createAiHttp`，把返回的 Fetch 处理函数挂到同源网关。前端只传材料 ID，不传模型密钥或身份范围。真实模型验收先使用合成 PNG/PDF/DOCX 和隔离租户，不用用户上传的业务制度。这个 SQLite 原型按操作者隔离草稿，不是共享审批项目的协同存储。

生产 AI 与材料集成尚未验收，见[企业试点](enterprise-pilot.md)。
